# stigref — Detailed Analysis (July 2026)

**Date:** 2026-07  
**Scope:** Full project review (pipeline, data, frontend, CI). No production content changes were part of the review itself.  
**Status:** Findings accepted; high-priority remediations tracked below and in [BACKLOG.md](BACKLOG.md).

---

## Overall verdict

The project is in strong shape for a small, focused repo. The stack is modern, the bundle is lean, the documentation is thorough, and features claimed as shipped exist in code. Weaknesses concentrate in three places:

1. **Error handling that can hide failures** in the data pipeline  
2. **Operational gaps** (stale KEV risk, no refresh automation, unpinned deps)  
3. **Frontend polish** (no tests, thin a11y, a few UX dead-ends)

Local `main` tracks `origin/main`; the Pages site is live: https://edodev.github.io/stigref/

---

## What's working well

- **Current stack, minimal surface:** Svelte 5 (runes), Vite 6, TypeScript strict, MiniSearch as the only runtime dependency. Production JS+CSS bundle is small (~133 KB class).
- **Sound pipeline:** parse → enrichment (tags, DISA packages, Intune CSP, threat) → write; `defusedxml` for XXE protection; nested-ZIP handling; stable IDs. Pytest suite exists under `scripts/tests/`.
- **Strong docs:** [BACKLOG.md](BACKLOG.md) (~70 items), threat-intel and version-history designs, help guide.
- **Verified product features:** search + facets + shareable URLs, STIG/rule detail + copy packs, KEV browser, Intune product hubs, bookmarks, themes, help, SPA 404 fallback.

## Findings by area

### Data pipeline (`scripts/stigref_build/`)

| Severity | Finding |
|----------|---------|
| High | KEV fetch used a blanket `except`, no retry, no JSON validation; cache read unguarded (corrupt cache → raw traceback). |
| Medium | Several stage-level `except Exception` handlers logged warnings and dropped enrichment (GPO/Intune packages, CKL, maps). |
| Medium | `requirements.txt` unpinned; no Dependabot; path assumptions via `__file__`. |
| Low | Test coverage ~10%; no fixture of a real DISA library ZIP or network mocks for KEV. |

### Data (`data/`, `raw/`)

| Severity | Finding |
|----------|---------|
| High (ops) | KEV snapshot can go stale without a scheduled refresh (weekly CISA updates). |
| Info | Only a handful of rules carry CVEs from XCCDF; KEV∩STIG overlap is near-zero — KEV tab remains useful as standalone browse. |
| Medium | ~100 MB+ committed data; multi-release plan in [VERSION_HISTORY.md](VERSION_HISTORY.md) not yet implemented (`data/releases/{date}/` + Release assets). |

### Frontend (`web/`)

| Severity | Finding |
|----------|---------|
| Medium | Zero unit/component/e2e tests. |
| Medium | Production source maps shipped (`sourcemap: true`). |
| Medium | Thin accessibility (few ARIA attributes; no skip link / live regions). |
| Low | UX: KEV hard-cap 200, no error retry, keystroke `replaceState`, `execCommand` clipboard fallback, limited breakpoints. |
| Low | No prerender — empty shell without JS (SEO). |

### CI / process

| Severity | Finding |
|----------|---------|
| High | Only Pages deploy workflow; no scheduled KEV or quarterly data refresh automation. |
| Medium | No Dependabot; Actions pinned to major tags, not SHAs. |
| Low | Commits rarely reference backlog IDs; B-018 CSP runbook incomplete; DESIGN.md size budget not validated in build. |
